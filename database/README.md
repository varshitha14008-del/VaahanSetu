# VaahanSetu — Database

PostgreSQL schema, seed data and constraint tests for VaahanSetu v2.0
(aligned with the *Updated SRS v2.0* and the *Updated Database Requirements,
Tables & Java Models* document).

## Files

| File | Purpose | Run order |
|------|---------|-----------|
| `vaahansetu_schema.sql`          | DDL only — 8 enum types, 15 tables, FKs, CHECKs, UNIQUEs, partial-unique indexes, triggers, comments. Re-runnable. | 1 |
| `vaahansetu_seed.sql`            | Small sample data (2 users, 4 buses, 7 stops, 2 routes, 3 trips, 4 journeys, 2 allocation runs, …). Re-runnable. | 2 |
| `vaahansetu_constraint_tests.sql`| 15 negative tests that prove the CHECKs, FKs, UNIQUEs, partial-unique rules and triggers actually fire. | optional, after 1+2 |

## Requirements

* PostgreSQL 13+ (developed on 18.6). The DDL uses:
  * `GENERATED BY DEFAULT AS IDENTITY`
  * `CREATE TYPE … AS ENUM`
  * partial unique indexes (`CREATE UNIQUE INDEX … WHERE …`)
  * `TIMESTAMP` / `TIMESTAMPTZ`
  * `plpgsql` triggers

## Apply the schema

From `psql` (as a superuser):

```bash
psql -h <host> -p <port> -U postgres -d postgres -c "CREATE DATABASE vaahansetu;"
psql -h <host> -p <port> -U postgres -d vaahansetu -f database/vaahansetu_schema.sql
psql -h <host> -p <port> -U postgres -d vaahansetu -f database/vaahansetu_seed.sql
# optional verification:
psql -h <host> -p <port> -U postgres -d vaahansetu -f database/vaahansetu_constraint_tests.sql
```

Or in one line:

```bash
psql -h <host> -p <port> -U postgres -d vaahansetu \
  -f database/vaahansetu_schema.sql \
  -f database/vaahansetu_seed.sql
```

## Application role

The schema creates a least-privilege role for the Java backend:

* role: `vaahansetu_app`
* password: `vaahansetu_dev_pwd`  ← **change this before any non-dev deployment**
* grants: `CONNECT` on DB; `USAGE` on `public` schema;
  `SELECT, INSERT, UPDATE, DELETE` on all current and future tables;
  `USAGE, SELECT` on all current and future sequences.

JDBC URL:

```
jdbc:postgresql://<host>:<port>/vaahansetu
```

## What is enforced in SQL vs. in Java

Per the *Database & Models* doc (section 3 — validation and calculation rules)
and section 8 ("Important SQL caveats"), some rules can only live in SQL,
others must live in the Java service layer.

### Enforced in SQL (this folder)

* Unique `username`, `bus.registration_number`, `route.route_code`.
* Positive `bus.capacity`; positive `route.estimated_duration_minutes`;
  non-negative `bus.rest_duration_minutes`; non-negative demand / capacity
  columns everywhere.
* `route_stops.stop_sequence > 0` and the `(route_id, stop_sequence)` PK
  guarantee a stable, ordered stop list per route.
* `UNIQUE (route_id, stop_id)` — no repeated stop per route (simplified model).
* `UNIQUE (route_id, departure_time)` — no duplicate departures per route.
* `UNIQUE (allocation_run_id, trip_id)` — exactly one outcome per trip per run.
* Partial-unique `uq_trip_one_active_assignment` — at most one `ACTIVE`
  assignment per trip.
* Partial-unique `uq_one_active_session` — at most one `ACTIVE` planning
  session at a time.
* Trigger `trg_route_stops_min_two` — block DELETE that would leave a route
  with fewer than two stops.
* Trigger `trg_pj_check_stop_order` — for each passenger journey, both stops
  must belong to the trip's route AND boarding must precede destination.
* Trigger `trg_pj_confirmations` — `alighting_confirmed_at` cannot be earlier
  than `boarding_confirmed_at`.
* Enum domains reject out-of-range status values at the DB level.

### Enforced in Java (service layer, not in this folder)

* Per-segment demand calculation (a passenger contributes to segments from
  boarding up to, but not including, destination).
* Bus schedule overlap detection (a bus cannot serve two simultaneous trips).
* Rest-period enforcement (next trip cannot start until previous trip ended
  + `rest_duration_minutes`).
* Transfer-time feasibility between previous endpoint and next start.
* Capacity check on every segment against the assigned bus.
* Demand simulation clamp at zero (5–10 passenger delta every 2 minutes).
* Single-transaction application of officer-approved reassignments.
* Whether `UNCONFIRMED` / `EXPIRED` registrations count toward planned
  demand — this is a team decision (see SRS section 9).

## Schema overview

```
users ─┐
       ├─→ planning_sessions ─┬─→ session_buses  ─→ buses
       │                       ├─→ session_routes ─→ routes ─→ route_stops ─→ stops
       │                       ├─→ passenger_journeys
       │                       ├─→ allocation_runs ─┬─→ allocation_assignments
       │                       │                    └─→ allocation_segment_results
       │                       └─→ segment_demand_adjustments
       └─→ trip_assignments ←─ scheduled_trips ←─ routes
```

## Open team decisions (PDF section 9) — NOT silently assumed

These are intentionally left for the team to decide and are NOT baked into
the schema:

1. Passenger identity (anonymous / journey token / passenger account).
2. When `UNCONFIRMED` journeys expire and whether they count toward demand.
3. Boarding/alighting confirmation mechanism (in-app, QR, …).
4. Route duration: one predetermined value per route (current schema) vs.
   per-trip override.
5. Transfer time between previous endpoint and next start.
6. Whether approved allocations immediately replace current assignments or
   only save the proposal.
7. Whether segment results are persisted (the table exists, optional) or
   calculated/displayed only during the session.
8. Persistence strategy: plain JDBC + DAO **or** JPA repositories — pick one.
9. The actual allocation algorithm and how it reduces unmet demand.

## Verification

`vaahansetu_constraint_tests.sql` runs 15 negative tests (each wrapped in a
PL/pgSQL `BEGIN … EXCEPTION` block so a single `psql -f` run reports all
results). Every test should report a constraint or trigger violation; if any
test reports `OK (no error)`, that rule is not being enforced.

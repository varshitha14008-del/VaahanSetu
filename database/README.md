# VaahanSetu — Database

PostgreSQL schema, seed data and constraint tests for VaahanSetu v2.0
(aligned with the *Updated SRS v2.0* and the *Updated Database Requirements,
Tables & Java Models* document).

## Files

| File | Purpose | Run order |
|------|---------|-----------|
| `vaahansetu_schema.sql`          | DDL only — 8 enum types, 15 tables, FKs, CHECKs, UNIQUEs, partial-unique indexes, triggers, comments. Re-runnable. | 1 (fresh installs only) |
| `vaahansetu_seed.sql`            | Small sample data (2 users, 4 buses, 7 stops, 2 routes, 3 trips, 4 journeys, 2 allocation runs, …). Re-runnable. | 2 (fresh installs only) |
| `vaahansetu_constraint_tests.sql`| 15 negative tests that prove the CHECKs, FKs, UNIQUEs, partial-unique rules and triggers actually fire. | optional, after 1+2 |
| `migrations/`                    | Incremental schema changes applied to an **existing** cloud DB. Each file is idempotent (safe to re-run). See `migrations/README.md`. | after the schema is already live |

### Applying changes to an existing cloud DB

If the schema is already deployed (e.g. on Neon) and you need to change
it, **do NOT re-run `vaahansetu_schema.sql`** — that drops all data.
Instead, write a numbered migration file in `database/migrations/` and
apply it directly to the cloud DB via the Neon SQL Editor or `psql`.

## Requirements

* PostgreSQL 13+ (developed on 18.6). The DDL uses:
  * `GENERATED BY DEFAULT AS IDENTITY`
  * `CREATE TYPE … AS ENUM`
  * partial unique indexes (`CREATE UNIQUE INDEX … WHERE …`)
  * `TIMESTAMP` / `TIMESTAMPTZ`
  * `plpgsql` triggers

## Running the database

You have two options. Pick **ONE** for the whole team — don't mix.

### Option A — Each person runs PostgreSQL locally

Best for independent development. Each teammate gets their own private
copy of the database at `localhost:5432`. No shared password to manage.

**Mac / Linux / WSL (one command):**

```bash
git clone https://github.com/varshitha14008-del/VaahanSetu.git
cd VaahanSetu
bash database/setup/setup.sh
```

The script auto-detects Docker or native PostgreSQL, spins up a fresh
Postgres 16, applies the schema + seed, and prints the JDBC URL.

**Windows:** install PostgreSQL from https://www.postgresql.org/download/windows/
(includes `psql`), then run:

```powershell
git clone https://github.com/varshitha14008-del/VaahanSetu.git
cd VaahanSetu
psql -U postgres -c "CREATE DATABASE vaahansetu;"
psql -U postgres -d vaahansetu -f database\vaahansetu_schema.sql
psql -U postgres -d vaahansetu -f database\vaahansetu_seed.sql
```

Local connection details (same for everyone):

| Field | Value |
|-------|-------|
| Host | `localhost` |
| Port | `5432` |
| Database | `vaahansetu` |
| Username | `postgres` (superuser) **or** `vaahansetu_app` (app role) |
| Password | `postgres` (superuser, Docker) **or** `vaahansetu_dev_pwd` (app role) |
| JDBC URL | `jdbc:postgresql://localhost:5432/vaahansetu` |

### Option B — Shared cloud PostgreSQL on Neon (recommended for team demos)

One shared database the whole team connects to. Best when everyone's app
needs to see the same data at the same time (e.g. for a final demo).

**One-time setup (one person does this, then shares details privately):**

1. Sign up at **https://neon.tech** (use GitHub OAuth — one click).
2. Click **Create new project**:
   - Project name: `vaahansetu`
   - Database name: `vaahansetu` (change from the default `neondb`)
   - Region: closest to your team (e.g. `ap-south-1` Mumbai for India)
   - Postgres version: 16
3. After creating, copy the **connection string** shown on the dashboard.
   It looks like:
   ```
   postgres://vaahansetu_owner:xxxxxxxx@ep-xxx.us-east-2.aws.neon.tech/vaahansetu?sslmode=require
   ```
4. Apply the schema + seed using the helper script:

   **Mac / Linux / WSL:**
   ```bash
   bash database/setup/apply_to_cloud.sh "postgres://vaahansetu_owner:xxxx@ep-xxx...?sslmode=require"
   ```

   **Windows (PowerShell):**
   ```powershell
   .\database\setup\apply_to_cloud.ps1 "postgres://vaahansetu_owner:xxxx@ep-xxx...?sslmode=require"
   ```

   The script is idempotent — re-running it drops and recreates the
   `public` schema, so it doubles as a "reset the DB" command.

5. **Share the connection details with teammates via a PRIVATE channel**
   (Slack, Discord, WhatsApp, iMessage — never in a git commit or repo
   README). Each teammate creates a local `.env` file (see below).

**Neon connection details (after setup):**

| Field | Value (example — yours will differ) |
|-------|-------|
| Host | `ep-cool-name-12345.us-east-2.aws.neon.tech` |
| Port | `5432` (default; Neon uses the standard port) |
| Database | `vaahansetu` |
| Username | `vaahansetu_owner` (Neon project owner role) |
| Password | (the long string Neon generated — share privately) |
| JDBC URL | `jdbc:postgresql://ep-xxx.neon.tech/vaahansetu?sslmode=require` |

> **SSL is mandatory on Neon** — always include `?sslmode=require` (or
> `?sslmode=require` in the JDBC URL). The schema itself doesn't enforce
> this; Neon does at the connection level.

**Connecting your Java app (both options):**

Copy `.env.example` (in the repo root) to `.env` and fill in your team's
values. The `.env` file is gitignored and will never be committed.

```bash
cp .env.example .env
# edit .env with your team's actual DB_URL, DB_USER, DB_PASSWORD
```

Then read those values from Java using
[dotenv-java](https://github.com/cdimascio/dotenv-java) or
`System.getenv(...)`. Example JDBC bootstrap:

```java
String url  = System.getenv("DB_URL");       // jdbc:postgresql://...
String user = System.getenv("DB_USER");      // vaahansetu_owner (Neon) or postgres (local)
String pass = System.getenv("DB_PASSWORD");  // Neon password or local password
Connection conn = DriverManager.getConnection(url, user, pass);
```

**Neon free-tier limits (as of 2026):**
- 0.5 GB storage (more than enough for this project's sample data)
- Always-on (does not sleep like Supabase's free tier)
- 1 project, 1 branch on the free plan
- Compute autoscales to zero when idle (cold start ~1s)

If you outgrow the free tier, the team can upgrade or move to a
self-hosted Postgres — the schema and seed SQL work identically anywhere.

## Application role

The schema creates a least-privilege role for the Java backend:

* role: `vaahansetu_app`
* password: `vaahansetu_dev_pwd`  ← **change this before any non-dev deployment**
* grants: `CONNECT` on DB; `USAGE` on `public` schema;
  `SELECT, INSERT, UPDATE, DELETE` on all current and future tables;
  `USAGE, SELECT` on all current and future sequences.

JDBC URL:

```
jdbc:postgresql://<host>:<port>/vaahansetu
```

## What is enforced in SQL vs. in Java

Per the *Database & Models* doc (section 3 — validation and calculation rules)
and section 8 ("Important SQL caveats"), some rules can only live in SQL,
others must live in the Java service layer.

### Enforced in SQL (this folder)

* Unique `username`, `bus.registration_number`, `route.route_code`.
* Positive `bus.capacity`; positive `route.estimated_duration_minutes`;
  non-negative `bus.rest_duration_minutes`; non-negative demand / capacity
  columns everywhere.
* `route_stops.stop_sequence > 0` and the `(route_id, stop_sequence)` PK
  guarantee a stable, ordered stop list per route.
* `UNIQUE (route_id, stop_id)` — no repeated stop per route (simplified model).
* `UNIQUE (route_id, departure_time)` — no duplicate departures per route.
* `UNIQUE (allocation_run_id, trip_id)` — exactly one outcome per trip per run.
* Partial-unique `uq_trip_one_active_assignment` — at most one `ACTIVE`
  assignment per trip.
* Partial-unique `uq_one_active_session` — at most one `ACTIVE` planning
  session at a time.
* Trigger `trg_route_stops_min_two` — block DELETE that would leave a route
  with fewer than two stops.
* Trigger `trg_pj_check_stop_order` — for each passenger journey, both stops
  must belong to the trip's route AND boarding must precede destination.
* Trigger `trg_pj_confirmations` — `alighting_confirmed_at` cannot be earlier
  than `boarding_confirmed_at`.
* Enum domains reject out-of-range status values at the DB level.

### Enforced in Java (service layer, not in this folder)

* Per-segment demand calculation (a passenger contributes to segments from
  boarding up to, but not including, destination).
* Bus schedule overlap detection (a bus cannot serve two simultaneous trips).
* Rest-period enforcement (next trip cannot start until previous trip ended
  + `rest_duration_minutes`).
* Transfer-time feasibility between previous endpoint and next start.
* Capacity check on every segment against the assigned bus.
* Demand simulation clamp at zero (5–10 passenger delta every 2 minutes).
* Single-transaction application of officer-approved reassignments.
* Whether `UNCONFIRMED` / `EXPIRED` registrations count toward planned
  demand — this is a team decision (see SRS section 9).

## Schema overview

```
users ─┐
       ├─→ planning_sessions ─┬─→ session_buses  ─→ buses
       │                       ├─→ session_routes ─→ routes ─→ route_stops ─→ stops
       │                       ├─→ passenger_journeys
       │                       ├─→ allocation_runs ─┬─→ allocation_assignments
       │                       │                    └─→ allocation_segment_results
       │                       └─→ segment_demand_adjustments
       └─→ trip_assignments ←─ scheduled_trips ←─ routes
```

## Open team decisions (PDF section 9) — NOT silently assumed

These are intentionally left for the team to decide and are NOT baked into
the schema:

1. Passenger identity (anonymous / journey token / passenger account).
2. When `UNCONFIRMED` journeys expire and whether they count toward demand.
3. Boarding/alighting confirmation mechanism (in-app, QR, …).
4. Route duration: one predetermined value per route (current schema) vs.
   per-trip override.
5. Transfer time between previous endpoint and next start.
6. Whether approved allocations immediately replace current assignments or
   only save the proposal.
7. Whether segment results are persisted (the table exists, optional) or
   calculated/displayed only during the session.
8. Persistence strategy: plain JDBC + DAO **or** JPA repositories — pick one.
9. The actual allocation algorithm and how it reduces unmet demand.

## Verification

`vaahansetu_constraint_tests.sql` runs 15 negative tests (each wrapped in a
PL/pgSQL `BEGIN … EXCEPTION` block so a single `psql -f` run reports all
results). Every test should report a constraint or trigger violation; if any
test reports `OK (no error)`, that rule is not being enforced.
